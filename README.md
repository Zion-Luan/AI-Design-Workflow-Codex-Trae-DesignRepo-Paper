# AI-Design-Workflow-Codex-Trae-DesignRepo-Paper


README
目的：不是让设计去干部分前端的活，而是借助 AI 改变交付方式，把对产品体验的控制权往前拿回来。
定位：不是为了 AI 一键提效，而是为了提升产品体验上限。
成本：它需要前期投入 —— 搭环境、整理资产、调组件。短期内不一定更快，甚至会更麻烦。
价值：设计交付可以不再停留在一次性静态稿，而是向可运行、可维护、可复用的资产推进。

Codex / Trae
AI Coding 工具，负责读代码、写组件、调样式和验证。大家都熟悉，不展开说
DesignRepo 
自建组件维护网站

DesignRepo 的目的在于：
让 AI 和设计师面对同一个真实系统 —— 设计师可在其上预览和工作，AI 也获得一套稳定的上下文。
- 基础系统层
产品最新 Token / Icon、基础组件，以及颜色、字体、间距、图标等通用规范。它解决的是“这套产品的基础语言是什么”。同时可以管理系统 token ，实现对基础组件的全局控制。
- 业务组件层
基于基础系统继续长出来的业务组件。每个组件都有真实可交互的 Preview，也有可复制的 Code；Token 更新后，引用它的组件可以一起响应。它解决的是“具体业务场景怎么被组件化、怎么被维护、怎么被交付”。
Paper 代码原生 AI 画布

为什么用 paper 而不是 figma：
代码原生，AI 还原几乎无损耗，且与 Design Repo 的“读”和“写”之间链路天然打通，流转损耗极低

🗻 背景
经历了 TRAE WORK（TRAE SOLO) 4月以及6月两个大版本的需求设计，发现了一些问题：
导致设计师被挤压在 "沟通 - 兜底 - 返工" 循环中，真正的设计创造空间极为有限。
设计时间被协作吞噬 🫪
设计师约 20-30% 时间用于需求沟通（且需求频繁变动），40-50% 用于走查和跨方协作（人和人的沟通有时候没有用...）。真正做页面设计的时间被极致压缩。
AI 让 Demo 易产出，但产品定义没变清晰 😁 
所以 AI 提升了协作方产出 demo 的速度，但没有自动提升上游输入的质量（很多 demo 只是把功能堆出来了，但是逻辑不一定正确，边界不一定清晰）。结果就是：别人看起来更快了，设计师要兜底的东西反而更多。
线上效果默认设计师“负责” 🤡
用户看到的是最终界面，不是 PRD，不是设计稿，也不是研发还原过程。无论问题来自哪里，最后通常都会变成：体验不好、页面不对。。。然后这些问题又回到设计师身上。这不是情绪化的归因问题。更准确地说，设计师的责任边界已经被线上效果重新定义了。
问题是：设计师对产品线上体验效果把控弱，设计师手里的工具和交付物还停留在静态稿阶段。这是最核心的矛盾

背景：TRAEWORK 品牌升级了，token & icon 都变了，所以我需要基于已有的组件仓库进行更新

于是把设计侧和组件侧的原料放到同一个工作目录里，主要包括三类：

- Icon SVG：把图标批量导出成 SVG，方便后续统一维护和调用。
- Storybook / 组件源码：在本地跑起来。一方面让 AI 读取组件结构，另一方面我也可以先看清楚仓库里有哪些组件、组件状态是什么。



3. 先让 AI 把这三类原料"扫描"成一份数据

我让 AI 写了一个生成脚本（ build-registry-data.mjs ）：
作用是把本地的 token JSON、图标 SVG、Storybook 索引这三个东西， 统一扫描成一份大的 JSON 文件 （ registry-data.json ），里面记录了所有 token、所有图标、所有组件的元信息。

4. 搭建 React  DesignRepo
[图片]

一开始我让 AI 用纯 HTML / CSS / JavaScript 搭了一版，Token 和 Icon 可以展示，但真实 React 组件跑不起来。TSX、组件依赖、状态、hover、点击、动效，都需要真实工程环境。
这次试错也让我意识到：如果原始代码仓库本来就是 React ，似乎就没有必要再降维转成 HTML 三件套。转换工作量很大，组件语义和交互还容易丢，最后也得再回到 React 工程里。
所以最终方案是直接保留 React 结构，用 Vite + React 搭DesignRepo。这样既能 import 研发已有组件，也方便后续让 AI 继续写新的 React 业务组件。

6. 把重复流程写成 Skill
暂时无法在飞书文档外展示此内容
暂时无法在飞书文档外展示此内容
做了几个组件后，我发现每次给 AI 的要求都很像：查 Token、查图标、做 Preview、同步 Code、跑验证。
这类重复规则不应该每次重新解释，而应该固化成 Skill。

我常用的skill主要沉淀了两类：
- figma-to-paper-solo：从 Figma / Paper 设计稿还原组件时怎么做。
- solo-registry-interactive-component：在 DesignRepo 里新增交互组件时怎么做。
Skill 里写清楚：
- 去哪里查 Token
- 图标找不到怎么办
- Preview 和 Code 怎么同步
- 新组件放在哪里
- 验收标准是什么
这样后面提需求时，就不需要每次从头教 AI。只要让它按对应 Skill 执行，它就会先读规则，再按同一套标准做组件。

1. 还没有解决“分享给别人用”的问题
现在这套东西本质上还是一个自己搭起来、自己能跑通的小产品。
但如果要让别人也能直接用，问题还没有完全解决。这里可能涉及打包、依赖环境、组件资源路径等一系列事情，我目前还没有完全理清😂。
2. DesignRepo 目前仍然是无奈之举
我做 DesignRepo 的本质是因为设计师不方便在仓库大改特改。实际用起来这个 DesignRepo 小产品，也有一些bug。自建组件网站能解决 GUI、Preview、Code、组件沉淀等问题，但它需要持续维护。
更理想的未来，是 TraeWork Design 或类似产品直接吃掉这件事：
- 接入真实组件仓库
- 提供面向设计师的 GUI
- GUI 管理仓库 Token 和 Icon
- 支持设计师拉设计分支
- 允许设计师安全修改组件
- 最后交给研发 CR 和工程化整理
设计师未来的工作方式，可能会更像研发拉分支：在自己的分支里探索、修改、验证，然后合回主系统。
3. 暂未强化研究代码规范
后续需要继续研究如何加强生产级代码规范（maybe 研发一起沉淀一套代码规范 Skill？或者强化现有 Skill，让 AI 在写组件时更严格地遵守团队的组件规范、命名规则和 Token 使用方式。）

🤔 更多的思考
1. 做这个流程的时候为什么不是从 Design Skill 开始
从来源看，一个 Skill 往往来自已有资产：可能是 Figma 设计系统，也可能是代码仓库里的组件和规范。我们先基于这些资产做总结和抽象，再形成 Skill。
所以本质上，Skill 是对现有资产的总结。调用 Skill 时，更像是在 消费 这些已经被总结好的规则。它很适合帮助我们快速完成从 0 到 80% 的生成和试错，但不太能解决另一个问题：随着业务发展和需求增加，新的组件、规范和交付资产怎么继续被生产出来。
这也是为什么我更倾向于先打通真实代码仓库。现代前端组件本身就是结构化的代码，规范、状态、样式和组件关系都白纸黑字落在里面。AI 读代码比读截图、读说明更直接；如果能调用真实组件，还原度也会更高。
2. 为什么想要和代码仓库打通
目的是想让，设计工作进入一个可以循环的系统。
代码仓库的价值在于，它同时解决“生产”和“消费”两个问题：组件被创建后进入仓库，后续需求可以继续基于它修改；Token 更新后影响已有组件；业务组件沉淀后又能被新的页面复用。
这样 AI 流程才不是一次“生成”，而是一个正向循环：生产资产、消费资产、再更新资产。这个循环一旦成立，设计师和研发才有可能真正共用同一套代码底座。
3. 为什么不是 HTML 原型，而是一开始就进入 React / 工程结构
HTML 和 React 之间不是无损转换。
HTML 更像表现层，适合表达页面“长什么样”；React 是工程结构，里面有组件、状态、交互、依赖和数据边界。先做 HTML，再让研发转成 React，似乎是在增加一层翻译？设计先消费一次 HTML，研发再生产一次 React，中间会平白增加损耗。
既然我们依托的代码仓库本来就是 React，就没有必要先绕到 HTML 里做设计，再让研发转回 React。更合理的方向，是从一开始就围绕可运行的 React 原型协作。
我对未来的想象是：设计师和研发不再围绕一份“待翻译的 HTML”协作，而是围绕一套可运行的 React 原型协作。
也许，这套原型可以保留两层接口：
- mock provider：用于设计师和业务方对需求、聊场景、验证流程。
- real provider：用于研发接真实后端接口。
两者保持同一套数据结构和调用边界。设计阶段先用 mock 跑通体验，研发接入时再切到 real。这样设计讨论不会被后端进度卡住，研发接入时也不用推翻前面的前端结构。
4. AI 时代，画布仍然很重要
设计一开始往往不是一个确定答案，而是一团还没成型的判断。这个阶段如果直接进入 Coding Agent，很容易被困在一个既定方案里，然后不断优化这个答案。看起来在推进，实际只是在消耗 token。
设计里最有价值的部分，恰恰是那些还不确定的阶段：发散、试错、推翻、重组、比较。这个过程需要画布，需要一个可以快速摆放、拖动、观察和反悔的空间。
Claude Design、v0 这类产品抓住了“代码化”的表象，但没有完全抓住设计流程本身。更擅长从 0 到 1 出页面，不擅长从 80 到 100 打磨体验。
所以 AI 不应该替代画布，而应该进入画布。Paper 的价值也在这里：它不是让画布消失，而是降低画布和 AI 工具之间“读”和“写”的损耗，再通过代码原生特性把设计结果继续送进组件和交付链路。
